## 范围

用户 2026-11-07 报告：输入框里的后续建议文字（ghost）与光标没有对齐，并要求“建议文字的顶边和行高对齐到输入框第一行：叠加层改用和输入框相同的起点和行高，不再在 36px 高度里居中”。同一轮对照 BoardUI AI Chat 的审查又发现三处相关问题，一并修复：

| 编号 | 问题 | 修复 |
|---|---|---|
| A | 没有附件时仍画出空附件行，输入卡片实际 107px（设计 96），文字上方空白约为下方两倍 | 只有存在附件时才传入附件行 |
| B | 建议文字按卡片内边距定位且在 36px 框内居中，比真实输入文字高 8px（BYOP）/ 10px（J Agent） | 输入框与建议层共用固定行高 `composerLineHeight`（14→20、15→21），建议层以输入框内容左上角为起点、高度等于行高 |
| C | 状态行和“Pi 正在工作”比输入文字左移 12.5 / 11.5px：0.19.2（`f257435`）把左边距误写成上边距 | 四处行元素改为只设左内边距 `composerTextInset(p)`（卡片内边距 + 边框） |
| E | 状态行已显示上下文容量时，输入框配件行重复显示容量 | 状态行确实含非空容量项时才隐藏配件行的容量胶囊 |

另修正 `main.go` 中残留的 `appVersion = "0.21.0"`（P29 漏改）。不改颜色、字号、动画、P29/P30 文件。

## 开发与审核

- 开发：GLM 5.3-Flash（`glm-5.3-flash`，关闭思考），独立副本。
- 审核：Cursor Claude Opus 5.5 @1m。
  1. 首轮：几何对齐、`FixedLineHeight` 副作用、交互、48 种外观/对比度/宽度组合的左对齐全部正确；**修复后允许提交**，P2×2：容量去重条件 `!hudVisible` 太宽（状态行只有分支时容量从界面消失）；去重测试是空测（找 "200K" 而界面显示 "1M"）。
  2. 修复：新增 `piHUDShowsContextCapacity()`，两套外观共用；去重测试改为 `tt.Texts()` 精确计数，增加“只有分支的状态行”场景；去掉两处只为测试新增的无障碍 Label；补 J Agent 建议字号断言；恢复 `p11_test.go` 被放宽的原场景。
  3. 复审：上轮两个 P2 关闭，无新代码问题；审核方在临时副本做了 5 种逆向修改（无条件绘制容量、改回 `!hudVisible`、J Agent 字号改回 14、附件行总是传入、新判断函数恒为真），每种都有测试失败。结论“修复后允许提交”，只要求补齐本文档两处悬空引用（已补）；P3 建议把卡片顶边像素扫描的容差从 ±0.5 放宽到 ±1（扫描返回整数像素，BYOP 输入框顶在半像素），已采纳；字宽断言余量 1px，字体大幅变化时可能漏报，由“文字盒高 = 行高”断言兜底。
- 逆向验证（开发席在临时副本中执行，审核方复验）：无条件绘制容量胶囊 → “状态行含容量”断言失败；改回 `!hudVisible` → “只有分支”断言失败；J Agent 建议字号改回 14 → 字宽断言失败（54 vs 57px）。首轮审核另验证：去掉 `FixedLineHeight` 墨迹差 2px、恢复 36px 居中差 8/9px、附件总是传入时卡片内距 24.5≠12.5、状态行恢复上边距差 −12.5/−11.5，均被测试捕捉。

## 可见变化与已知限制

- 输入框固定行高后多行输入略高：两行 36→40px，十行上限 165→200px（J Agent 177→210）；最小窗口 760×560 下发送按钮与状态行仍在可视区。字形不会被裁切（行高取固定值与字体实际高度的较大者），光标与选中高亮随行高变高，滚动不受影响。
- 原生占位提示文字下移 1–2px，与输入文字第一行一致。
- 直接点击建议文字本身不会聚焦输入框（0.22.0 起已有，与本次无关）；点击输入框其它区域正常。
